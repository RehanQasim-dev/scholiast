## [2026-08-23 00:30] task-05 agent
- **What I learned (mid-work bugs found by gates/review):**
  1. Chrome.tsx imported `{ commands }` as a named export before the bridge exported it → every control dispatch was `undefined.setRate`. Fixed: `commands` is now a module-level export referenced by the `playerBridge` singleton.
  2. First bridge design routed poll emissions back through `emit("onTimeUpdate")` via an internal listener — infinite synchronous recursion. Poll now patches the store and emits once, directly.
  3. `attach()` originally relied on YT's native `onReady` for readiness; fakes (and reality: YT fires it late) left `ready=false` so all command guards no-op'd. Redesign: `attach()` starts a session immediately (the IFrame API queues player-method calls made before internal readiness), while the native `onReady` listener became a late hook that re-reports metadata/captions and flushes pending loads — this also fixes late title/duration arrival on slow-loading videos.
  4. StrictMode/lifecycle review caught: after `detach()` + re-`attach()` of the SAME player instance, listeners were never re-registered (second visit to `/player` = video plays, zero events). Fixed with a `listening` flag; test extended to prove poll resumes post-reattach.
  5. `YTPlayerLike.setOption` needed the real 3-arg signature `(module, option, value)`.
- **Decisions made:** Readiness is per-attachment (`detach` clears it; re-attach re-emits `onPlayerReady`) so Player.tsx's resume-seek works on every route entry, not just first load. `seekTo` patches the store optimistically so chrome UI is instant. Volume clamped 0–100 in the bridge. ENDED emits a final `onTimeUpdate(duration)` like player.html.
- **Progress:** All deliverables implemented: `src/player/playerBridge.ts`, `PlayerHost.tsx`, `Chrome.tsx`, rewritten `src/routes/Player.tsx`, generic `src/components/Toast.tsx`. Tests: 6 bridge + 5 Chrome.
